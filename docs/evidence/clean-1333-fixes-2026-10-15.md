## 1 Empty height became `1024*1024`
- Search: `rg "(\|\||\?\?) ?(1024|512|768)\b" src` found four silent fills, and none of them is a server or Schema default.
  1. **ParameterInspector width/height inputs:** `onChange: parseInt(v) || 1024`. Clearing the height in the right panel wrote 1024 straight away. That write reached the Empty Latent through App's inspector write-back (`EmptyLatentImage.values.height = newParams.height`).
  2. **App inspector mirror:**
     - It used `height: graphExtraction?.height ?? (Number(latent.height) || Number(ckpt.height) || 0)`. With a connected Empty Latent whose height was empty, the panel showed the CheckpointLoader's stale `height` (1024, written back during the earlier Krea run).
     - Any panel edit, such as switching the model, then wrote `newParams.height` back into `EmptyLatentImage.height`. The empty field was refilled silently.
  3. **Asset → frame and AssetManager:** `asset.width ?? 1024` and `item.width || 1024`.
  4. **Spatial EmptyLatent edit:** `Number(undefined)` gave NaN.
- **Root cause:** the value came from the CheckpointLoader node (`values.width/height`, written by the panel) or from the inspector input's `|| 1024`. It reached `EmptyLatentImage.values.height` through the App inspector write-back. graphEngine and the server add nothing (the graphEngine fix was in clean-1351).
- **Caveat:** 画布's clean-1333 outcome.json says 02b had "Empty Latent 1024x1024 explicit". From the code I can't tell whether the tester typed 1024 or one of the paths above filled it. Either way, both paths are now gone.
- **Fix:**
  - The inspector inputs write `undefined` when cleared.
  - The mirror takes size only from a connected Empty Latent (`sizeOrUndef`), and from the Checkpoint only when no Empty Latent exists. It never uses 0 or a stale value.
  - The asset paths use `undefined`. The spatial path uses `sizeOrUndef`.
- Files: src/components/ParameterInspector.tsx, src/App.tsx, src/components/AssetManagerModal.tsx, src/utils/localBlock.ts.

## 4 Krea select + run made two Schema GETs
- **Root cause:**
  - The second GET (13:37:53) came from the server, not the browser. Its route was `/api/schema-provider/wavespeed/submit`, upstream `/api/v3/models`.
  - The submit handler called `modelSchema()` on every submit, so it re-read the catalog Schema even though `GET /api/model-schema` had just read it at select time.
  - The client did reuse its shared GET; the browser log had one GET.
  - Venice did the same thing (two GETs per submit: models plus swagger), as did the blocked z-image run (05:40:17).
- **Fix:**
  - `GET /api/model-schema` stores the definition per provider + model + sha256(key).
  - Submit reuses it (`schemaRead.reused`, `reusedFrom:'/api/model-schema'`, `note:'复用，未重新请求'`) and only reads upstream when nothing is stored (`schemaRead.fetched`).
  - A new `GET /api/model-schema` (refresh) always re-reads upstream and replaces the stored entry. Failures are not stored.
- **Client:** when the run reuses the select-time shared result, the driver writes a LOCAL row 「Schema 复用 · provider · model — 复用，未重新请求 · 0 个请求」. Group headers count LOCAL rows separately and not as requests.
- Files: src/server/schemaProviders.ts, src/engines/drivers/SchemaProviderDriver.ts, src/services/sharedGet.ts, src/components/ExecutionLog.tsx, src/services/executionTrace.ts.
