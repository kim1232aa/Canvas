## 1. Run gate grey, panel 「未选择」, while the node shows the model
**Root cause.** The clean-0935 restore strip did NOT remove the selection. The e2e board's stored workspace was read from the test browser's on-disk localStorage; only structure was extracted, no keys. It has `ckpt_name: wavespeed-ai/z-image/turbo` and `targetProvider: wavespeed` intact.

What the board lacks is the edge 「加载底模」 MODEL → 「Load LoRA」 model. It has 9 connections: lora → KSampler.model exists, and ck → lora.clip exists, but the MODEL edge into the LoRA does not. An earlier board in another profile had that edge.

The cause was not found. Restore code never touches connections, so it was lost by some earlier edit. The data wasn't changed.

The real defects were three different readers of "the selected model":
- The node label read the loader's values.
- The Run gate and the panel re-traced the MODEL chain from the sampler. When the chain was broken they got nothing, and showed a generic 「请先选择模型」 / 「未选择」.
- With the loader selected, `resolveRunTarget` refused (「不是可运行的输出节点」). The gate also extracted from the selected node id, not from the run target.

**Fix.**
- **One source for provider and model.** `resolvedActive` in App.tsx is the branch loader's values. It is traced through the chain when connected, and otherwise read from the loader directly. The panel forces checkpoint and targetProvider from it, because `readInspectorParameters` no longer overrides them.
- **One target for gate, label and run.** The gate extracts from `runTargetState.target`. A selected loader or LoRA resolves to the single downstream output node; if there are zero or several, the old message stays.
- **The break is named.** `modelChainBreak()` in graphEngine reports, for example: 「底模连线断开：「Load LoRA」的 model 输入没有连接「加载底模」的 MODEL…」. It is used by extraction (the gate) and shown in the panel (`modelChainIssue`). No auto-reconnect and no fallback model.
- **Schema-driven verification.** 选用此 ID / 应用为底模 leave a non-catalog ID as 「尚未核实」. A 200 Schema GET for exactly that provider+model now marks it verified. A failed GET keeps it unverified, with the verbatim error in the exec log.

**Files:** `src/App.tsx`, `src/utils/graphEngine.ts`, `src/components/ParameterInspector.tsx`.

**To fix the e2e board itself:** reconnect 加载底模 MODEL → Load LoRA model. The gate now says exactly this.

## 2. Every explicit model selection sends exactly 1 Schema GET
**Root cause.** The clean-0935 gate only counted `ProviderModelSelect.onChange` as a user action. Typed IDs, 选用此 ID and 应用为底模 only changed props, which the editor ignores by design.

**Fix.** New `src/services/userModelSelection.ts`:
- `noteUserModelSelection(provider, model)` starts a new action and makes one shared Schema GET.
- `schemaRequestFor()` provides the URL and headers shared by the editor, the badge cache, the selection call and the driver.

Callers:
- the node 自定义 ID input and the inspector ID input, on commit (blur or Enter, only if the value changed; not per keystroke)
- the node dropdown
- `handleSelectModelFromHub`, which covers 选用此 ID and 应用为底模

`ApiParameterEditor` never fetches on a prop change; it peeks and subscribes. Mount, hydrate and StrictMode still send 0 GETs.

**Files:** `userModelSelection.ts` (new), `ApiParameterEditor.tsx`, `modelSchemaCache.ts`, `ProviderModelSelect.tsx`, `NodeItem.tsx`, `ParameterInspector.tsx`, `App.tsx`.
